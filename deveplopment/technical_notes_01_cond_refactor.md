# 技術ノート — フェーズフリーBCPフレームワーク実装記

## 第1回：`cond`機構の解読と層0フィルタへの拡張

### 1. まず、既存の`cond`は何をしているか

`bcp_disaster_src.html`（地震版・v1.3系）の評価項目は、`ITEMS`という配列に23項目並んでいる。各項目はこういう形をしている。

```js
{ cat:'診療系', id:'d_dialysis', label:'透析_部門', states:['m','s','x'], cond:'d_dialysis' }
```

`cond`は「この項目を画面に表示するかどうかの条件」を表す文字列だ。実際に判定しているのが`isVisible`関数。

```js
function isVisible(cond) {
  if (cond === 'always') return true;
  if (cond === 'emr')    return !!document.getElementById('d_emr')?.checked;
  if (cond === 'icu')    return !!document.getElementById('d_icu')?.checked;
  return !!document.getElementById(cond)?.checked;
}
```

読み解くと、判定は3パターンしかない。

1. `cond`が`'always'`なら無条件で表示する（電源・通信・上下水道など、どの病院にもある設備）
2. `cond`が`'emr'`か`'icu'`なら、病院プロフィール画面にある対応チェックボックス（`id="d_emr"` / `id="d_icu"`）を見る
3. それ以外（`d_or`、`d_dialysis`等）は、**`cond`の文字列をそのままDOM要素のIDとして使い**、そのチェックボックスの状態を見る

3番目が肝心な部分だ。「透析部門を持っていますか」という病院プロフィールの入力欄のIDが`d_dialysis`で、評価項目側の`cond`も同じ`d_dialysis`という文字列になっている。つまり**文字列が一致してさえいれば、新しい診療科が増えても`isVisible`関数自体は1行も変えなくていい**という設計になっている。これは筋の良い設計で、今回もこの「文字列一致で自動的につながる」という発想は壊さずに引き継ぐ。

### 2. なぜこれをそのまま複数の判定軸に拡張できないか

今回、層0フィルタを「診療機能（`cond_function`）」と「施設・立地属性（`cond_facility`）」の2軸に分けると決めた。理由は、両者が性質の違う情報だから。

- 診療機能（ICUがあるか、透析部門があるか）は、病院が**自分の意思で持つ/持たない**を決めている恒常的な属性
- 施設・立地属性（浸水想定区域内か、活火山からの距離）は、病院の意思とは無関係な**外的な地理的事実**

この2つを同じ`cond`という1本の文字列に混ぜたままだと、地震のITEMSを眺めたときに将来水害用の`flood_risk_zone`が視界に紛れ込み、「これは診療科の話なのか、立地の話なのか」を毎回文脈で判断しなければならなくなる。データ構造として分けておいた方が、後で人が読むときにも、プログラムが処理するときにも迷わない。

### 3. 改修方針：`cond`を単一文字列から複合オブジェクトへ

```js
// 変更前
{ id:'d_dialysis', cond:'d_dialysis' }

// 変更後
{ id:'d_dialysis', cond: { function: 'd_dialysis' } }
```

`function`だけの項目は今まで通りの意味（診療機能チェックボックスの状態を見る）。新たに`facility`キーを追加できるようにする。

```js
// 水害の新規項目イメージ
{ id:'flood_teisuiban', cond: { facility: 'flood_risk_zone' } }
```

`function`と`facility`が両方指定されていれば、AND条件（両方満たしたときだけ表示）として扱う。これは例えば「透析部門があり、かつ浸水想定区域内にある病院」だけに出す項目を将来作りたくなったときに対応できる余地を残すため。

### 4. `isVisible`関数の書き換え

呼び出し側（`getVisible`）は`ITEMS`を`isVisible(it.cond)`でフィルタしているだけなので、`isVisible`の中身だけ直せば呼び出し側5箇所（`buildTable`、`renderRecoveryItems`、`calcFuzzy`、`gatherData`、`buildHistoryTicketHTML`）は無改修で済む。これは既存コードが「判定ロジックを1関数に閉じ込めていた」おかげで、影響範囲が最小化されている。

```js
// 変更後のisVisible
function isVisible(cond) {
  // 旧形式（文字列）との後方互換：既存の呼び出しが残っていても壊れないようにする
  if (typeof cond === 'string') {
    cond = { function: cond };
  }

  let result = true;

  if (cond.function) {
    result = result && checkFunctionCond(cond.function);
  }
  if (cond.facility) {
    result = result && checkFacilityCond(cond.facility);
  }

  return result;
}

function checkFunctionCond(fn) {
  if (fn === 'always') return true;
  if (fn === 'emr')    return !!document.getElementById('d_emr')?.checked;
  if (fn === 'icu')    return !!document.getElementById('d_icu')?.checked;
  return !!document.getElementById(fn)?.checked;
}

function checkFacilityCond(facility) {
  // 施設・立地属性も同じ「文字列一致でチェックボックスを見る」思想を踏襲
  return !!document.getElementById(facility)?.checked;
}
```

`typeof cond === 'string'`の分岐を残したのは、既存の23項目をすべて書き換えなくても動くようにするため。実際には今回、地震版のITEMSも新形式`{ function: ... }`に統一するので実運用でこの分岐が使われることはないが、移行期の安全弁として残す。

**運用ルール（今回確定）**：こうした「今は不要だが保険として残すコード」には、除去のタイミングと理由を明記したTODOコメントを必ず添える。コメントなしで「そのうち消す」と決めると、最終リリース前の一括除去の際に見落とされる。今後このプロジェクトで同種の保険コードを書く場合、このルールで統一する。

```js
// TODO(v2.0リリース前に削除): 旧cond文字列形式との後方互換用。全ITEMSを複合形式に統一したら不要。
if (typeof cond === 'string') {
  cond = { function: cond };
}
```

### 5. 水害の最小限ITEMS（動作確認用）

地震のITEMS構造をそのまま踏襲し、`cond`だけ複合形式にした最小サンプル。

```js
const FLOOD_ITEMS = [
  { cat:'設備系', id:'flood_teisuiban', label:'止水板設置状況', states:['m','s','x'], cond:{ facility:'flood_risk_zone' } },
  { cat:'診療系', id:'flood_dialysis',  label:'透析_部門（1階配置の場合）', states:['m','s','x'], cond:{ function:'d_dialysis', facility:'flood_risk_zone' } },
];
```

2項目目は意図的に`function`と`facility`の両方を指定した。「透析部門があり、かつ浸水想定区域内」という複合条件が実際に機能するかを確認するための項目。これがα版での最小検証範囲になる。

### 6. まだ解いていない問題

`checkFacilityCond`は`checkFunctionCond`とほぼ同じ中身（DOM要素のIDを見るだけ）になった。これは今の時点では正しい（両方とも「病院プロフィール画面のチェックボックスを見る」という同じ操作だから）。ただし将来、施設属性の入力方法が変わる（例えばチェックボックスではなく「浸水深何cm想定」のような数値入力になる）場合は、この関数だけ個別に書き換えが必要になる。今は関数を分けておくこと自体に価値がある。分けておけば、片方だけ仕様が変わっても影響範囲が閉じる。

`isVisible`の改修が済んだので、次はこれを実際に`ITEMS`配列と組み合わせて`getVisible()`を通し、複合条件が正しくフィルタされるかを確認する。あわせて、水害用の評価スコア計算（ITEM_WEIGHTS・trapezoidパラメータを水害用に別テーブル化する部分）に着手する。

## 第2回：ITEMS統合とMEMBERSHIP_PARAMSのバグ

### 1. 方針転換：ITEMSを種別ごとに分けず、単一配列に統合する

第1回では「地震のITEMSはそのまま、condだけ複合形式にする」という前提で進めていたが、議論の結果、ITEMS自体を統合する方針に転換した。

理由は、`cond:'always'`だった項目（一般電源・発電機・通信・上下水道・医療ガス・エレベーター）は、実は地震固有の項目ではなく、水害でも降灰でも同じように評価対象になるべき**オールハザード項目**だったから。これを地震用・水害用で別々に定義すると、同じ「一般電源」という概念を種別ごとに複製することになり、「種別BCPへのアンチテーゼ」という心意気に反する。

そこで各ITEMに`weight_by_disaster`という種別別の重みテーブルを内包させ、ITEMS配列自体は1本にまとめた。

```js
{ id:'infra1', label:'一般電源', cond:{function:'always'}, weight_by_disaster:{earthquake:5} }
{ id:'flood_teisuiban', label:'止水板設置状況', cond:{facility:'flood_risk_zone'}, weight_by_disaster:{flood:8} }
```

`weight_by_disaster`にキーが無い種別では、その項目は評価対象外になる（後述の判定式）。今の時点ではオールハザード項目（infra系等）にも地震の重みしか入っていない。水害・降灰のITEMS設計が本格化した時点で、これらの項目にも`flood: X`、`ashfall: Y`を追記していく。

### 2. 表示・評価の判定式

「この項目を今の病院・今の災害種別で評価するか」の判定は、2つの条件のANDになる。

```
表示可否 = 層0条件(cond.function / cond.facility)を満たす
           AND weight_by_disaster[現在の種別] が定義されている
```

前半（層0条件）は第1回で作った`isVisible`がそのまま担当する。後半（種別条件）は新しく`getVisible()`に追加した。

```js
function getVisible() {
  return ITEMS.filter(it =>
    isVisible(it.cond) &&
    it.weight_by_disaster && (it.weight_by_disaster[currentDisasterType] !== undefined)
  );
}
```

電子カルテのように「層0では絞られるが、全種別で重みを持つ」項目と、止水板のように「層0でも種別でも絞られる」項目は、どちらも同じこの1本の式で処理できる。前者は`weight_by_disaster`に3種別分のキーが揃っているだけで、式の構造自体は変える必要がない。

### 3. 見つかったバグ：スコアのスケール感の取り違え

水害用に`MEMBERSHIP_PARAMS`を仮値で作った際、境界値を`{a:0, b:0, c:3, d:6}`のような0〜30点台のスケールで設定してしまい、**「全項目が最重度(x)」という入力でもlevel 0(平常)と誤判定される**バグを埋め込んでいた。

原因は、以前（不可逆加算方式を検討していた頃）の「累積スコア0〜30点台」という設計の名残を、可逆化・ファジー推論移行後のスコア設計に引きずってしまったこと。`calcFuzzy`が実際に計算している`score`は`totalScore / totalWeight`という**重み付き平均**であり、これは`STATUS_SCORES`（m:0, s:1, x:3）の範囲、つまり理論上0〜3にしかならない。0〜30点台の境界値をこの0〜3の値に対して適用すると、どんなに深刻な状態でも境界値に届かず、常に群0近辺に判定されてしまう。

これは実際に単体テストコードを書いて動かしてみて初めて発覚した。「全項目を最重度にしたら最悪の群になるはず」という最も基本的な期待値を確認するテストがなければ、この不整合は気づかないまま残っていた可能性がある。

### 4. 副産物：MEMBERSHIP_PARAMSはオールハザード共通でよいと判明

バグ修正のため水害のMEMBERSHIP_PARAMSを地震と同じ0〜3スケールに直したところ、境界値が地震のものと完全に一致した。これは偶然ではなく、次の事実に基づく。

- 地震のMEMBERSHIP_PARAMSの境界値（0.3, 0.5, 0.7…）は、災害の物理的特性から導かれたものではない
- 元は行動判断支援票の原案作成時、災害対策委員会に対して「このスコアならどう動くべきか」というアンケートを取り、その回答をファジー推論にかけて逆算したもの
- つまりこの境界値が表しているのは、地震固有の被害パターンではなく、**医療機能の深刻度に対する人間の行動判断の閾値感覚**
- 閾値感覚は災害の原因を問わない（電源が落ちた原因が地震でも水害でも、医療現場が取るべき行動の閾値は変わらない）

この結論により、`MEMBERSHIP_PARAMS`は種別で分けず、**単一のオールハザード共通テーブル**に統合した。種別ごとに変わるのは各ITEMの`weight_by_disaster`（何が重要かという重みづけ）だけで、「重み付き平均がどこから深刻とみなされるか」という境界そのものは共通になった。

```js
// 統合後：種別を問わない単一テーブル
const MEMBERSHIP_PARAMS = {
  0: { a: 0.0, b: 0.0, c: 0.3, d: 0.5 },
  1: { a: 0.3, b: 0.5, c: 0.7, d: 1.0 },
  2: { a: 0.7, b: 1.0, c: 1.3, d: 1.6 },
  3: { a: 1.3, b: 1.6, c: 2.0, d: 2.5 },
  4: { a: 2.0, b: 2.5, c: 999, d: 999 },
};
```

これは「オールハザードの心意気を実装レベルでどこまで徹底できるか」という問いに対して、当初の想定（重みも境界値も種別ごとに分ける）より一歩踏み込んだ答えが出た、という経緯として記録しておく。種別で本質的に異なるのは「何が重要か（重み）」であって、「深刻度の感じ方の境界（境界値）」は共通、という切り分けができたのは、実際にバグを踏んで初めて見えたことだった。

### 5. 単体テストで検証した内容

DOM依存部分（`document.getElementById`）を切り離し、`calcFuzzy`の計算ロジック部分だけをNode.jsで単体実行して検証した。

- 地震モードで地震専用項目のみが計算対象になり、水害専用項目は無視されること
- 水害モードで水害専用項目のみが計算対象になり、地震専用項目は無視されること
- 全項目が最重度(x)のとき、正しく最も深刻な群(level 4)になること（バグ発見の決め手）
- 全項目が正常(m)のとき、level 0になること
- 一部項目のみ軽度(s)のとき、中間的なlevelになること

構文チェックは`node --check`で、実HTMLファイルからscriptブロックを抜き出して実施した。

### 今後の作業

- 水害・降灰のITEMS本体（今は動作確認用の2項目のみ）を、水害タイムライン・富士山チェックリストの内容から本格的に書き起こす
- `currentDisasterType`は今のところ固定値。層0のUI（災害種別選択）は中身が揃ってから着手する方針
- オールハザード項目（infra系等）の`weight_by_disaster`に水害・降灰の重みを追記する

## 第3回：イベントレイヤーの発見、区画管理、印刷まわりのトラブルシューティング

### 1. 発見：ITEMSと外部トリガーは別物だった

水害の評価チェック項目（11項目）を実際にITEMSへ実装しようとしたところ、根本的な不整合が見つかった。ITEMSのstates（○△×）は「病院の設備・機能が壊れているか」を測る形式だが、「台風接近」「氾濫注意水位超」のような外部の状況進行はこの形式に馴染まない。台風接近に○△×を当てはめること自体が意味を成さない。

これにより、水害11項目は性質で2種類に分かれることが判明した。

- **外部トリガー型**（台風接近、氾濫注意水位超等）：病院の外で起きているイベント。決断の窓・通過点を開くトリガーとして機能する。ITEMSには含めない
- **被害結果型**（病院浸水）：外部イベントの結果として病院の設備・機能に実際に生じた状態。ITEMSにそのまま乗る（自院観測の一種）

重要な副産物として、地震の震度もこの枠組みに入ることが分かった。震度5強（幹部連絡基準）・6弱（自動参集基準）という自動参集基準は、本来イベントの`triggers`として明示すべきものだったが、地震版はこれまで「震度そのもの」をイベントとして構造化していなかった。これにより「本部立ち上げ」「幹部連絡」「自動参集」が独立した3つの通過点であることが判明し、震度と無関係にZERO HOURで開始する「本部立ち上げ」（施設内人員による最小構成）と、震度依存の「幹部連絡」「自動参集」を分離した（設計メモ9-6参照）。

イベントのスキーマ、判定基準の実例（水害・降灰・地震）、トリガー条件をノード側が持つ設計決定は設計メモ9章に整理済み。ここでは実装への示唆だけ記す。

### 2. ITEMSへの実装：24項目＋病院浸水1項目

イベントレイヤーの発見を踏まえ、水害・降灰固有のITEMS新設は最小限に留めた。

- 水害固有のITEMSは「病院浸水（内水氾濫）」の1項目のみ（`weight_by_disaster: {flood: 5}`）
- 降灰固有のITEMS新設は**不要**と判明。冷却塔閉塞・下水道の灰づまり・MRI/CT故障・空調フィルター目詰まりは、いずれも「原因が違うだけで壊れる対象は地震と同じ設備」であり、既存ITEMSに`ashfall`キーの重みを追記するだけで対応できた
- ただしこの過程で、地震のITEMS23項目に「空調設備」が存在しないという欠落が発覚した。降灰資料で最重要リスクとして扱われていたことがきっかけで見つかったが、「病院は温度変化に脆弱な患者が集中する場所」という論拠自体はオールハザードに効くため、`infra_hvac`として24項目目に追加し、重みは全種別で2に統一した

止水板・フィルター交換・冷却塔養生は、当初「建物防御」という6つ目のITEMSカテゴリとして構想したが、これも見直した。これらは「病院側が自分の意志で実行する作業」であり、イベントにもITEMS本来の趣旨（被害結果を測る）にも当てはまらない。アクションカード（層3）の実行結果として、通過点で記録する方式に変更した。結果、ITEMSのカテゴリは当初の5つ（インフラ系・医療ガス系・搬送系・情報系・診療系）のまま変わらなかった。

### 3. note/exampleフィールドの追加

ITEMSに`note`（重要性の補足説明）と`example`（ラベルから対象が想像しにくい項目の具体例）を任意フィールドとして追加した。運用ルールとして、全項目に一律追加するのではなく「ラベルから評価対象が一意に想像できるか」を個別判断する方式にした（例：`infra_hvac`にはexample「冷却塔、空調フィルター等」を付けたが、`infra1`一般電源には付けない）。

### 4. 区画管理（ゾーニング）を独立した中間レイヤーに

止水板の議論から派生して、降灰・水害・将来の感染症で共通して使う「区画管理」の原則が必要になった。当初アクションカードの1枚として検討したが、これは手順書ではなく「何を満たせば良い区画設計と言えるか」という原則の集合（原則型カード）であり、手順型カードとは抽象度の階層が違うと判明した。

最終的に、区画管理は層2（災害種別）と層3（アクションカード）の間に挟まる独立した中間レイヤーとして切り出した（設計メモ10章）。既存の医療機関向け感染対策ゾーニング指針（厚生労働省の急性期病院向けゾーニング指針）をそのまま踏襲し、独自の解釈は加えていない（`zoning_principles_v0.md`）。

### 5. 印刷まわりのトラブルシューティング：長い試行錯誤の記録

ここからは、今回最も時間を要した作業の記録。UIの微調整という性質上、設計メモ12章には残さない方針（12章はデータ構造・設計判断に限定）だが、同種のミスを繰り返さないための教訓として、この技術ノートには残す。

**発端**：カテゴリラベル（「医療ガス系」等の縦書き表示）が隣接カテゴリと重なって印刷される、という報告から始まった。

**第一の勘違い：文字サイズの問題だと決めつけた**
最初にratio（文字数÷行数）に応じてfont-sizeを動的に縮小するロジックを追加した。医療ガス系が2行（酸素・吸引圧のみ）のときに5文字を収めきれないという見立てで、「ガス系」への略称表示も同時に実装した。この時点では画面表示・履歴詳細印刷ともに改善したように見えた。

**第二の混乱：doPrint()経路とbuildHistoryTicketHTML経路を取り違えた**
その後「印刷するとまだズレる」という報告が来たが、報告されたPDFがどちらの印刷経路（`doPrint()`＝Step1〜3を直接印刷、`buildHistoryTicketHTML()`＝履歴詳細からの印刷）から出力されたものか確認せずに、間違った経路のCSSを何度も調整した。2つの経路は完全に独立したクラス体系（`cat-td`系 対 `kt2-cat`系）を持っており、一方を直しても他方には影響しない。

**第三の発見、そして繰り返し：colgroupの見落とし**
`buildHistoryTicketHTML`側で、CSSクラス（`.kt2-cat { width: ... }`）をいくら変更しても列幅が変わらない現象に直面した。原因は、HTML側に`<colgroup><col style="width:13pt">...`という直接指定が既に存在し、これがCSSクラスの`width`より優先されていたことだった。colgroupを36ptに広げて解決した。

ところがこの直後、`doPrint()`側（`#mainTable`）で全く同じ症状（widthを変更しても効かない）が再発した。**前者で学んだはずの教訓（colgroupの存在を疑う）を、後者では最初に確認しなかった**。`#mainTable`にも`<colgroup><col style="width:20px">`が最初から存在し、これが印刷側CSSの`.cat-td { width: 16pt !important }`より優先されていた。同じ原因を2回、別々の箇所で踏んだことになる。

**方針の右往左往**
この過程で、印刷側の動的計算（ratio縮小ロジックの印刷版）を追加しては削除し、`table-layout: fixed`を追加しては削除し、`!important`の有無を何度か入れ替えた。最終的に「白紙帳票のfuzzyScoreクリア漏れ」まで含めて、指定されたポイント（fuzzyScore実装直後）まで一度全て巻き戻す指示を受けた。巻き戻し後、動的フォントサイズ縮小ロジック自体（画面表示・履歴詳細印刷の両方）も削除し、カテゴリラベルは常に固定サイズで表示する方式に落ち着いた（略称処理「医療ガス系」→「ガス系」は残した）。

**真相：ブラウザ依存だった**
最終的に、Chromeで開くと巻き戻し後の状態で正しく表示されることが確認された。DuckDuckGoブラウザ・Safariでは`writing-mode: vertical-rl`のレンダリングに差があり、印刷結果がずれる。これはCSSで完全に吸収しようとすると際限のない調整になるため、「印刷はChrome推奨」という運用上の注記で対応することにした（README・運用ガイドに追記）。

**この節から得た教訓（設計メモ12-6に追記済み）**：
1. 同じ問題（列幅のはみ出し）が起きたら、CSS数値の調整より先に**colgroupの存在を確認する**。CSSクラスより優先順位が高い指定が別にある可能性を疑う
2. 複数の独立した印刷経路（`doPrint()`と`buildHistoryTicketHTML()`）がある場合、修正前に**どちらの経路の出力かを必ず確認する**。見た目の類推だけで直す場所を決めない
3. ブラウザ間の描画差（特に`writing-mode`のような比較的マイナーなCSS機能）は、CSS側の調整で完全には吸収しきれないことがある。無理に全ブラウザ対応を追わず、推奨環境を明記する判断も選択肢に入れる
